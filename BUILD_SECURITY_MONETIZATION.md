# Сборка, безопасность, монетизация и публикация

## 1. Инструкция по сборке

### Требования

Для сборки проекта нужны:

- Android Studio с установленным Android SDK;
- JDK 21;
- подключение к интернету для загрузки Gradle-зависимостей;
- файл `app/google-services.json` для Firebase;
- API-ключ OpenWeatherMap.

Основные параметры приложения:

- `applicationId`: `com.stepanov_ivan.weatherwearadvisor`;
- `minSdk`: 28;
- `targetSdk`: 36;
- `compileSdk`: 36;
- `versionCode`: 1;
- `versionName`: `1.0`.

### Настройка API-ключа

Ключ OpenWeatherMap можно указать в `local.properties`:

```properties
OPENWEATHERMAP_API_KEY=your_api_key
WEATHER_API_BASE_URL=https://api.openweathermap.org/data/2.5/
```

Также ключ можно передать через Gradle property или переменную окружения `OPENWEATHERMAP_API_KEY`.

Файл `local.properties` не должен попадать в публичный репозиторий, потому что в нем могут находиться локальные пути и секретные ключи.

### Debug-сборка

Команда сборки:

```bash
gradlew.bat clean assembleDebug
```

Готовый APK:

```text
app/build/outputs/apk/debug/app-debug.apk
```

Установка на устройство:

```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

### Тесты

Unit-тесты:

```bash
gradlew.bat test
```

Инструментальные тесты:

```bash
gradlew.bat connectedAndroidTest
```

### Release-сборка

Перед release-сборкой нужно:

- проверить `versionCode` и `versionName`;
- подключить production `google-services.json`;
- указать рабочий API-ключ OpenWeatherMap;
- настроить подпись приложения через keystore.

Сборка APK:

```bash
gradlew.bat assembleRelease
```

Сборка AAB для Google Play:

```bash
gradlew.bat bundleRelease
```

Готовый AAB:

```text
app/build/outputs/bundle/release/app-release.aab
```

## 2. Описание безопасности приложения

### Аутентификация

Приложение использует Firebase Authentication для регистрации, входа и выхода пользователя. Пароль пользователя не хранится в локальной базе приложения: проверка учетных данных выполняется на стороне Firebase.

После успешного входа локально сохраняются только `user_id` и email. Они нужны для восстановления состояния сессии и привязки данных гардероба к конкретному пользователю.

### Защищенное локальное хранение

Для хранения `user_id` и `user_email` используется `EncryptedSharedPreferences` из AndroidX Security Crypto:

- master key создается через Android Keystore;
- используется схема `AES256_GCM`;
- ключи preferences шифруются через `AES256_SIV`;
- значения preferences шифруются через `AES256_GCM`.

При выходе из аккаунта зашифрованные локальные данные очищаются.

### Локальная база данных

Гардероб пользователя и кэш погоды хранятся в Room-базе `weather_wear_db`.

Для защиты пользовательских данных в репозитории гардероба проверяется владелец данных:

- чтение вещей разрешено только текущему пользователю;
- добавление, изменение и удаление вещи выполняется только при совпадении `currentUserId` и `item.userId`;
- при попытке доступа к чужим данным возвращается ошибка.

Текущая Room-база не шифруется целиком. Если в будущем приложение будет хранить более чувствительные данные, стоит добавить шифрование базы, например через SQLCipher.

### Сетевые запросы

Погодные данные загружаются через OpenWeatherMap API по HTTPS:

```text
https://api.openweathermap.org/data/2.5/
```

Для сети используются Retrofit и OkHttp. В приложении настроены таймауты и обработка типовых ошибок: отсутствие интернета, timeout, ошибки API и превышение лимита запросов.

Перед публикацией рекомендуется отключить сетевое логирование в release-сборке или оставлять его только для debug, чтобы не раскрывать лишнюю диагностическую информацию.

### Геолокация

Приложение использует разрешения:

- `ACCESS_FINE_LOCATION`;
- `ACCESS_COARSE_LOCATION`.

Геолокация нужна только для получения погоды по текущему местоположению. Пользователь может выбрать город вручную, поэтому приложение не должно требовать доступ к геолокации без необходимости.

### Разрешения

В манифесте используются:

- `INTERNET` для Firebase и OpenWeatherMap;
- `ACCESS_NETWORK_STATE` для проверки состояния сети;
- `ACCESS_FINE_LOCATION` и `ACCESS_COARSE_LOCATION` для погоды по координатам.

Приложение не запрашивает доступ к SMS, контактам, камере или микрофону.

### Работа с секретами

API-ключ OpenWeatherMap передается через `local.properties`, Gradle properties или переменные окружения. Такой способ удобен для разработки, но ключ все равно может быть извлечен из APK.

Для production-релиза рекомендуется:

- использовать разные ключи для debug и release;
- не публиковать ключи в репозитории;
- по возможности ограничить ключ на стороне сервиса;
- при развитии проекта вынести погодные запросы на backend-proxy.

### Что проверить перед релизом

Перед публикацией нужно:

- проверить Firebase Authentication;
- проверить работу OpenWeatherMap API;
- отключить лишнее логирование;
- настроить backup/data extraction rules;
- подготовить privacy policy;
- заполнить Data safety форму в Google Play.

## 3. План монетизации

Для первой версии лучше выбрать мягкую freemium-модель: основное приложение остается бесплатным, а дополнительные удобные функции становятся платными.

Бесплатная версия:

- просмотр погоды;
- базовые рекомендации по одежде;
- выбор города вручную;
- ограниченный гардероб.

Платная версия:

- неограниченный гардероб;
- сохранение готовых комплектов;
- рекомендации на несколько дней вперед;
- несколько профилей, например для семьи;
- отсутствие рекламы, если она будет добавлена.

Этапы внедрения:

1. Сначала выпустить приложение бесплатно и собрать обратную связь.
2. Потом добавить Premium-функции, которые действительно нужны пользователям.
3. После этого подключить оплату через Google Play Billing.

Для учебного проекта достаточно указать, что основной вариант монетизации - freemium, а платежи планируется реализовать через Google Play Billing.

## 4. Простой план публикации

Публикацию можно разделить на несколько шагов.

1. Подготовить приложение:

- проверить основные экраны;
- исправить критические ошибки;
- обновить `versionCode` и `versionName`;
- собрать release AAB;
- подписать приложение release-ключом.

2. Подготовить страницу в Google Play:

- название приложения;
- краткое и полное описание;
- иконку;
- скриншоты;
- категорию;
- контактный email;
- ссылку на privacy policy.

3. Заполнить обязательные формы:

- возрастной рейтинг;
- Data safety;
- информацию о рекламе;
- целевую аудиторию.

4. Провести тестирование:

- загрузить AAB во внутреннее тестирование;
- проверить вход, регистрацию, выбор города, геолокацию, гардероб и рекомендации;
- исправить найденные ошибки.

5. Выпустить приложение:

- перевести сборку в открытое тестирование или production;
- после публикации следить за ошибками, отзывами и статистикой использования.

После первого релиза можно постепенно улучшать рекомендации, добавлять Premium-функции и готовить следующие версии приложения.
